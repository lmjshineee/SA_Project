# 多智能体智能办公汇报系统项目规范

版本 0.1　日期 2026年10月28日

本规范约定三人课程实验的功能、开发边界和验收依据。系统接收办公汇报需求，由五个 Agent 协作读取本地资料、整理数据、撰写和审核业务汇报。实验报告负责说明系统如何搭建与运行；系统生成的业务汇报是实验产物，两者分别提交和说明。

## 1 要求依据

### 1.1 用户明确要求

| 编号 | 要求 | 设计对应 | 实际完成的证明 |
| --- | --- | --- | --- |
| U01 | 框架不限 OpenClaw，可任选开源框架 | LangGraph 编排，Streamlit 展示 | 环境记录、依赖版本、开源来源 |
| U02 | 完成多智能体搭建和工作 | 五角色协作、工具使用、审核返工 | 五角色运行记录、完整任务输出 |
| U03 | 三人一组 | 三人分工开发五个 Agent | 分工、代码贡献、个人总结 |
| U04 | 最终提交实验报告 | 按报告模板记录过程和结果 | 完成并核对的课程实验报告 |
| U05 | 记录搭建过程和运行截图 | 环境记录、运行编号、截图索引 | 搭建步骤、原始截图及对应日志 |

设计覆盖要求不代表实验已经通过。U01—U05 的实际验收须在实现与运行后逐项核对。

### 1.2 参考指导书的采用方式

保留智能办公汇报场景与 Manager、Planner、Data、Writer、Checker 五种角色，保留单 Agent 开发、协作调试、体系结构图、时序图及架构分析的实验主线。将原有五人分工调整为三人共同开发五个角色。

不沿用参考文件中未经验证的安装命令、框架实现细节、社区数据、免费额度和设备性能判断。后续安装依据所选框架的官方文档，以实际环境验证结果为准。

| 参考交付项 | 本项目处理 |
| --- | --- |
| 单 Agent 代码、测试与日志 | 纳入实现与验收计划 |
| 协作日志、架构图、时序图、问题记录 | 纳入基线 |
| 两个正常任务演示 | 纳入基线，补充异常测试 |
| 独立不少于 2000 字的架构分析报告 | 报告模板预留分析章节；独立文件和字数按课程确认结果执行 |
| 演示视频、答辩 PPT、现场答辩 | 参考交付项，待确认 |
| 连续运行 30 分钟 | 参考稳定性实验；执行时记录时长、任务数和空闲时间 |
| Docker 部署、PDF 导出 | 可选扩展，本地部署和 Markdown 导出作为基线 |

若老师后续补充提交要求，先更新要求映射和实施计划，再安排新增工作。

## 2 功能范围

### 2.1 输入与输出

用户输入汇报主题、部门、季度和重点内容，选择本地样例资料。基线接受 UTF-8 CSV 与 TXT 文件，输出大纲、证据数据、Markdown 草稿、审核记录和最终业务汇报。

典型输入：生成2026年第二季度技术部工作汇报，包含项目进度、人员考勤和成果统计。

演示界面展示需求、阶段进度、各 Agent 的结果摘要、数据来源、审核问题和导出入口。输入不完整时展示待补充项；所需数据不存在时明确终止本次运行，保留原因。

### 2.2 功能要求

| 编号 | 功能 | 必须满足的行为 | 验证用例 |
| --- | --- | --- | --- |
| F01 | 需求接收 | 解析部门、季度、重点和输出格式；缺少关键字段时返回待补充项 | T01、T05 |
| F02 | 大纲规划 | 输出带稳定章节编号的大纲和每章数据需求 | T02、T03、T04 |
| F03 | 数据整理 | 根据计划选择允许的本地工具，读取快照、筛选部门季度、计算指标 | T02、T03、T04、T06 |
| F04 | 报告撰写 | 按大纲和证据生成结构化草稿、指标引用及 Markdown 内容 | T02、T03、T04 |
| F05 | 审核 | 同时检查结构、指标一致性、来源及内容完整性，输出具体问题 | T02、T07、T08 |
| F06 | 协作和返工 | 记录角色交接；按问题类型返回 Writer、Data 或 Planner，最多返工两轮 | T03、T07、T08 |
| F07 | 展示和导出 | 展示进度、阶段结果和审核记录；仅合格结果可导出为最终业务汇报 | T03、T04、T08、T11 |
| F08 | 异常处理 | 对超时、无效模型输出、数据错误作有限处理，保留可定位错误 | T05、T06、T09、T10 |
| F09 | 运行追溯 | 每次运行拥有独立编号、输入快照、配置摘要、事件日志和产物索引 | T01—T12 |
| F10 | 实验交付 | 三人贡献、搭建过程、截图、测试结果、问题与分析能汇总进实验报告 | T12 |

### 2.3 多智能体成立条件

每个 Agent 必须有独立角色指令、职责、上下文选择、结构化输出和验证记录。上游结果必须被下游实际使用，交接日志须记录发送者、接收者和产物引用。Data 必须通过模型决策调用允许的工具，接收工具结果后再生成数据说明；Checker 的意见必须能影响后续执行。

五个普通函数、五条固定输出或一次模型调用被显示为五个角色，均不满足本项目的多智能体验收标准。LangGraph 节点、文件工具、数值校验和导出函数是实现组件，不能仅凭节点数量计为 Agent。

五个角色可复用同一模型服务，不要求独立进程或网络服务。体系结构描述应如实说明采用单进程中的逻辑协作。

## 3 Agent 职责

| 角色 | 负责内容 | 主要输出 | 主责成员 |
| --- | --- | --- | --- |
| Manager | 解析需求、识别缺项、形成任务说明 | `TaskSpec` | A |
| Planner | 设计章节、重点及数据需求 | `ReportPlan` | B |
| Data | 选择读取与统计工具、整理证据、说明数据限制 | `EvidenceBundle` | B |
| Writer | 根据大纲和证据撰写，按审核意见修订 | `ReportDraft` | C |
| Checker | 核对结构、数据与来源，提出修复建议 | `ReviewResult` | C |

路由、计数、超时、最终放行和文件导出由编排层的确定性规则负责。模型提出的修复目标必须经过枚举校验，不能自行增设角色、工具或无限循环。

## 4 数据规范

### 4.1 资料与字段

实验使用明确标注为模拟办公数据的资料，不使用真实个人考勤或内部业务资料。模拟数据仍须完整保留，使另一名成员能够独立复算。

| 文件 | 必需字段 | 校验规则 |
| --- | --- | --- |
| `projects.csv` | `project_id, department, period, name, status, progress_percent` | ID 唯一；状态限 `planned/in_progress/completed/blocked`；进度为 0—100；完成项目进度为 100 |
| `attendance.csv` | `member_id, department, period, scheduled_days, attended_days` | 同部门季度内成员 ID 唯一；天数非负；实到不超过应到 |
| `achievements.csv` | `achievement_id, department, period, category, title` | ID 唯一；标题和类别非空 |
| `service_feedback.csv` | `feedback_id, department, period, score` | ID 唯一；分值为 1—5 的整数 |
| `notes.txt` | 首两行为 `department: 部门` 和 `period: YYYY-Qn`，其后为正文 | UTF-8；部门季度与请求一致；保留原文行号 |

每个样例场景使用独立资料目录。`period` 采用 `YYYY-Q1` 至 `YYYY-Q4`，部门名称使用一致的全称。结构化数据按部门和季度过滤后计算；TXT 的范围由文件头识别。文件损坏、必需字段缺失、重复 ID 或非法数值须报错，不能静默删除后继续。

基线限制单个文件 5 MiB、单次最多 10 个文件；这些是本项目的实现目标，实施时验证并记录。运行服务将用户选定的资料保存为输入快照；Agent 的资料读取和产物写入限制在本次运行目录内。

### 4.2 指标口径

| 指标 | 计算方法 | 边界处理 |
| --- | --- | --- |
| 项目数 | 过滤后有效项目 ID 数 | 零个项目须说明资料为空 |
| 完成项目数 | 状态为 `completed` 的项目数 | 不把进行中项目计入完成数 |
| 项目完成率 | 完成项目数 ÷ 项目总数 × 100% | 分母为零时标为不可计算 |
| 出勤率 | 实到天数总和 ÷ 应到天数总和 × 100% | 不使用个人出勤率的简单平均；分母为零时不可计算 |
| 成果数 | 过滤后有效成果 ID 数 | 不由模型猜测成果数量 |
| 满意度 | 得分不低于 4 的反馈数 ÷ 有效反馈总数 × 100% | 同时展示满意数和总样本量；空反馈不可计算 |

数值计算由程序工具完成，使用明确的十进制和四舍五入规则：比例保留两位小数，先计算后舍入。模型只负责选择工具、解读结果和组织文字。

业务协议使用 `Decimal`，JSON 以十进制字符串或整数传值，拒绝浮点数与布尔值；比例的原始值为 0—100 的百分数，展示值不附带单位。具体字段、容量与指标键见[业务数据协议](业务数据协议.md#3-证据与指标)。这些结构校验不代替真实数据工具的计算和来源核验。

每项指标附带指标 ID、原始值、展示值、单位、计算口径及来源引用。来源引用至少包括输入快照相对路径、SHA-256、行号或记录 ID。人工检查应能沿此信息找到原始数据。

### 4.3 缺失资料

Manager 和 Planner 共同确定本次需求的必需资料。必需文件缺失、没有对应部门季度的数据，或必需指标因零分母而无法计算时，返回 `needs_input`，列出缺项，并保存已有阶段产物；补充资料后新建一次运行。

可选章节缺少资料可以省略或说明“未提供资料”，不得编造事实。若用户明确要求该章节，不能将其静默改为可选。完成率为零与资料不足是不同状态。

## 5 质量与运行约束

| 维度 | 基线要求 |
| --- | --- |
| 可复现 | 记录操作系统、Python、依赖、模型及参数、代码版本、输入哈希；重跑应得到相同的确定性指标，文字可有差异 |
| 可追溯 | 每个模型调用、工具调用、角色交接和审核决策均关联 `run_id`；保留各轮产物 |
| 有限执行 | 最多返工两轮；单个模型请求默认超时 60 秒，单次运行总期限 600 秒；模型调用总次数上限 30 |
| 可解释失败 | 使用 `needs_input`、`needs_review`、`failed` 区分终止原因；失败时保留日志，不产生合格标记 |
| 输出可靠 | 结构化指标须与工具结果一致，审核引用的草稿版本须与最终导出版本相同 |
| 数据隔离 | 不同运行目录隔离；界面刷新不重复启动任务；跨会话不混用运行状态 |
| 配置保护 | 密钥从环境变量或本地配置读取；截图、日志、提交包不含密钥原文 |
| 工具边界 | 只允许指定资料读取、统计、格式检查与导出；拒绝路径越界，不执行模型生成的任意命令 |

模型输出、工具参数和状态更新均须做结构化校验。源文件中的文字视为资料，不得作为修改系统指令、工具权限或路由规则的依据。自然语言审核仍可能遗漏问题，应保留最终人工核对步骤，不能声称系统能保证任意文本完全准确。

具体超时、调用次数和返工限制见[架构设计](架构设计.md)。上述数值是设计限制，实际耗时、成本和稳定性必须测量后填写。

## 6 开发与协作规范

1. Python 文件使用 UTF-8；模块、函数和字段采用一致命名；公共接口提供类型与简短说明。结构化对象使用 Pydantic 校验。
2. 角色指令与编排代码分离；模型接入封装为统一接口；工具保留可独立调用的确定性实现。
3. 统一 `schema_version`、角色 ID、状态枚举和错误码。修改共享字段时同步更新架构文档、上下游调用方和相关验证。
4. Agent 只提交允许的状态增量；全局计数、日志序号和最终状态由编排层维护。
5. 用例应验证真实约束，如统计口径、交接数据、审核路由和失败终止。替身模型测试与真实模型实验分开记录。
6. 采用可追溯的版本管理和小批次提交，按[合作准则](合作准则.md)在每个可独立验证的改动后及时 commit，并在本次工作结束前推送工作分支，经 PR 和同伴检查合并。依赖在验证兼容后固定版本；不把“使用最新版”作为可复现说明。
7. 联调问题按“位置 → 原因 → 修复 → 验证”记录。每位成员提供实际负责代码、测试与报告章节的依据。

## 7 验收规则

实际验收清单和证据索引在[实验实施计划](实验实施计划.md)中统一维护。至少包含：

1. 环境搭建、真实模型连通和五角色独立验证。
2. 两个正常业务场景，包含完整的输入、交接、审核和输出证据。
3. 一次可复现的审核拒绝和修订，以及返工达到上限的终止验证。
4. 缺少资料、非法数据、模型故障和无效输出的验证。
5. 三人贡献记录、真实截图、完整日志及完成后的课程实验报告。

所有未执行项标注“未执行”，受设备或服务限制的项目标注实际原因。不得用设计截图、替身模型输出或编辑后的日志替代真实运行证据。
