# 三人小组合作准则

版本 0.1　日期 2026年10月28日

本准则用于三人共同完成多智能体课程实验。目标是让每次改动及时保存、能够复查，并使代码、运行证据和个人贡献保持一致。

仓库为 [lmjshineee/SA_Project](https://github.com/lmjshineee/SA_Project)，公开可见，主分支为 `main`。三名成员各自使用本人 GitHub 账号和 Git 身份，成员姓名、账号与实际分工在实验报告中填写。

## 1 工作范围

开始修改前，先检查现状，列出拟修改项、受影响文件和验证方法，经用户明确同意后实施。已经批准的范围内直接推进，commit 和向工作分支 push 无需逐次确认；新增功能、改变技术路线或扩大交付范围时重新确认。

认领任务时说明负责内容、接口依赖和完成条件。任务可以记录在 PR 或项目文档中，不要求为了小改动额外创建大量记录。成员之间同步影响协作的决定，避免多人同时修改同一份共享契约而互不知情。

## 2 三人职责与交接

| 成员 | 主责 | 重点交接 |
| --- | --- | --- |
| A 组长 | Manager、共享状态、编排、运行服务与日志 | 向 B、C 提供需求、状态、消息、错误和生命周期约定 |
| B | Planner、Data、资料工具、样例和指标口径 | 向 C 提供大纲、证据结构、指标 ID、来源和预期值 |
| C | Writer、Checker、界面与导出 | 向 A 反馈审核结构、返工目标和展示所需事件 |

模块由主责成员维护，其他成员可以参与，但修改前要核对当前工作和接口影响。共享状态、消息格式、指标口径等变更需要受影响成员检查，代码与文档同批更新。

每人保留自己实际完成的提交、测试、调试和报告章节。使用 AI 辅助时，由成员核对结果并承担对应代码与内容的解释责任，不预先填写贡献比例或代写虚构的个人经历。

## 3 分支与主分支

`main` 保存经过小组检查的成果。任务在独立分支完成，示例名称为 `feat/manager-workflow`、`feat/planner-data`、`feat/report-review`、`docs/setup-guide` 或 `fix/metric-validation`。

开始新任务前查看 `git status` 和当前分支，获取远端状态，再从最新 `origin/main` 建立分支。工作区有其他成员或用户的改动时先保留并确认归属，不自动执行丢弃、覆盖或清空操作。

持续开发时将 `origin/main` 的更新合入任务分支，解决冲突后执行受影响的验证。不强推共享分支，不重写别人已经使用的历史。一个任务分支尽量只包含一个目的的改动。

仓库初始化为一次已批准的例外：初始文档和协作配置分成两次提交放入 `main`。后续更新通过 PR 评审合并。默认采用保留有效提交历史的 merge；如需整理提交历史，由参与者在合并前明确约定。

## 4 及时 commit 与 push

每完成一个可独立说明、可验证的改动单元就提交，例如需求解析、一个统计工具、审核路由，或一批相关文档修正。不要把多人的不同模块和无关修改堆成一个“大更新”。同一目的的细小修改可以合并为一笔提交。

提交前按顺序执行：

1. 查看差异并确认文件归属，只暂存本次任务相关文件或代码块。
2. 完成与改动匹配的验证。文档核对链接、结构与事实；代码验证契约、指标或执行分支。没有执行的检查如实说明。
3. 审阅 `git diff --cached`，执行 `git diff --cached --check`，确认没有误带配置、运行资料或其他成员的工作。
4. 用准确说明创建 commit，随后继续下一个改动单元。
5. 本次工作结束前 push 到对应分支，并核对本地提交与远端同步。

提交标题使用 `type(scope): 变更说明`，scope 可省略，例如：

```text
docs: add experiment specification and architecture
feat(data): add attendance metric calculation
fix(workflow): stop after revision limit
test(checker): cover mismatched metric references
chore: establish repository collaboration rules
```

标题描述实际变化，必要时在正文说明原因、验证和限制。不使用“全部完成”“测试通过”等无法由该提交证明的结论。

未完成工作需要保存时，可以用 `chore(wip): ...` 提交并推送，PR 标为草稿，说明剩余内容。推送失败须保留本地提交并记录原因，不能把本地 commit 等同于远端已保存。

## 5 PR 与评审

PR 使用[统一模板](../.github/pull_request_template.md)，说明问题、变更后的行为、验证结果和协作影响。可独立验证的任务对应一个 PR，避免单个 PR 混入无关模块。

合并前至少一名其他组员检查。评审关注输入输出是否一致、工具和审核是否实际执行、失败路径是否明确、数据能否复算，以及文档与证据是否真实。涉及共享契约时，由受影响模块的负责人检查对应变化。

作者处理反馈后补充提交，并更新验证结果。评审人明确同意后，由小组约定的合并者执行合并；不得替评审人填写同意意见。AI 助手可以整理变更和验证记录，但不能充当另一名组员伪造同伴评审。

这些是小组的流程约定。当前未配置 GitHub 服务端分支保护或必过 CI，不应把 PR 模板中的复选框当成服务器已经执行的检查。

## 6 公开资料与实验记录

仓库公开。密钥、真实个人考勤或内部资料、本地模型权重和虚拟环境保留在本地；配置只提交 `.env.example` 等脱敏示例。`.gitignore` 只是避免误加入文件的辅助，不能代替暂存差异检查。

完整运行目录保存在本地 `runs/`，按实施计划用于实验提交包和复现。经检查且适合公开的必要日志、截图和指标样例可单独复制到 `evidence/` 并建立索引；未审核资料放在本地 `evidence/raw/`。不要为了保留证据而对整个忽略目录强制添加。

证据注明 `run_id`、模式、模型、代码版本和来源。替身模型测试、受控注入与真实运行分开说明；原始日志不手工改写，修订产物保留版本。公开提交的个人信息由本人核对，贡献记录按真实参与填写。

## 7 冲突与问题处理

多人修改同一文件时，先比较各自改动的目的和对应任务，保留必要修改，再执行相关验证。不能仅以“使用我的版本”解决语义冲突。

问题记录遵循“位置 → 原因 → 修复 → 验证”。共享接口问题同步上下游，已合并缺陷用新的修复提交处理。需要回退时说明影响，使用可追溯的 revert；不通过强推隐藏历史。

## 8 每次工作结束

1. 记录完成的内容、commit 哈希、所在分支及 push 结果。
2. 记录实际执行的验证和未执行项；实验运行补充编号及证据位置。
3. 将仍需他人处理的接口、问题或评审事项写清楚。
4. 查看工作区，说明遗留改动的归属，不自动清理他人文件。
5. 同步必要文档，使下一名成员能据此继续。
