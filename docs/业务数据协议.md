# 业务数据协议

版本 `1.0`，实施日期 2026年10月30日。对应[架构设计第 4.2 节](架构设计.md#42-业务对象)，实现位于 `src/office_agents/schemas/`。

本批次实现五角色未来使用的业务载荷和纯校验函数，尚未实现 Agent、共享状态、交接消息、文件读取或流程路由。接口需 A、B、C 交叉检查后用于各自模块。

## 1 交接结构

| 上下游 | 对象 | 本批次校验 |
| --- | --- | --- |
| Manager → Planner | `TaskSpec` | 需求字段、季度、输出格式、缺项一致性 |
| Planner → Data/Writer | `ReportPlan`、`PlanSection` | 章节 ID、必需章节、指标白名单 |
| Data → Writer/Checker | `EvidenceBundle`、`Metric`、`Excerpt`、`SourceRef` | 数值、展示值、单位、来源定位、显式缺项 |
| Writer → Checker | `ReportDraft`、`DraftSection`、`FactClaim` | 章节与声明归属、证据值、产物引用 |
| Checker → 未来编排层 | `ReviewResult`、`ReviewIssue` | 结论一致性、审核对象版本、问题定位、修复优先级 |

所有对象的 `schema_version` 默认 `1.0`，拒绝其他版本、未知字段和隐式类型转换。文本必须包含非空白字符，但保留原文，不自动裁剪。ID 使用字母、数字、下划线、点和短横线；不使用本机路径充当 ID。

## 2 需求与大纲

`TaskSpec` 的 `title/department/period` 在缺项时用 `null` 表示；`required_sections/input_file_ids` 可以为空，但 `missing_fields` 必须准确列出相应缺项。缺项标识只接受这五个字段名，不能缺而不报，也不能把已有字段标为缺失。`output_format` 仅为 `markdown`，季度采用 `YYYY-Q1` 至 `YYYY-Q4`。

`ready_for_planner` 只表示需求的已知必需字段齐备，不表示输入文件存在或需求已经过人工确认。`validate_plan(task, plan)` 要求每个用户必需章节标题都在大纲中且 `required=true`。大纲的章节 ID 和标题唯一，章节中的指标键不得重复。

## 3 证据与指标

| `metric_key` | 单位 | `display_value` |
| --- | --- | --- |
| `project_count` | 个 | 整数字符串 |
| `completed_project_count` | 个 | 整数字符串 |
| `project_completion_rate` | % | 两位小数字符串 |
| `attendance_rate` | % | 两位小数字符串 |
| `achievement_count` | 个 | 整数字符串 |
| `satisfied_feedback_count` | 条 | 整数字符串 |
| `feedback_count` | 条 | 整数字符串 |
| `satisfaction_rate` | % | 两位小数字符串 |

这些键落实已有指标口径，满意度额外明确满意反馈数和总样本量的键。公式仍按[项目规范](项目规范.md#42-指标口径)，本批次不实现统计计算或验证公式是否来自工具。

Python 的 `raw_value`、`FactClaim.value` 使用 `Decimal`；JSON 推荐使用十进制字符串，也接受整数。拒绝浮点数、布尔值、非有限值、负数和超过 28 位数字容量的输入。百分比的原始值在 0—100 内，表示百分数本身，例如 `"60"` 表示 60%，不是 0.6。展示值不含单位；比例按 `ROUND_HALF_UP` 保留两位小数，计数必须为整数。校验保留原始值，不先舍入再替换原值。

每项指标至少有一条来源。`SourceRef` 包含 `file_id`、`snapshot_path`、64 位小写十六进制 SHA-256，以及记录 ID 或包含首尾行的 `[start, end]`；行号从 1 开始，CSV 包含表头。来源路径必须为 `inputs/` 下的规范相对路径，拒绝绝对路径、URL、反斜线、`.`、`..`、空路径段和控制字符。

`Excerpt` 包含 `excerpt_id/text/source_ref`，保留原文和位置。`EvidenceBundle` 的指标 ID、指标键和摘录 ID 各自唯一。`missing_required` 中缺失指标使用指标键；其他必需资料缺项可使用明确的资料标识，原因写入 `limitations`。同一指标不能同时存在和缺失。

`validate_evidence(plan, evidence)` 检查必需指标已提供或已明确标缺。它允许带缺项的部分证据保存；`ready_for_writer=false` 时，`validate_draft` 拒绝进入完整写作交接。零值可以是合法结果，未知值不能用零代替。

## 4 草稿与审核

`DraftSection` 包含 `section_id/content/claim_ids`。草稿中的每个声明必须归属一个存在的章节，并由该章节引用；引用不允许悬空、跨章节或重复。`validate_draft` 进一步要求章节属于大纲、必需章节齐备、每章必需指标都有声明，以及所有声明的数值和单位与证据一致。

草稿的 `plan_ref/evidence_ref`、审核的 `draft_ref/evidence_ref` 必须为 `artifacts/` 下的规范相对路径，并与调用方传入的当前产物引用一致。`validate_review` 还比较当前草稿 SHA-256；缺失章节的问题可引用大纲中尚未出现在草稿里的章节 ID。其他问题的章节、声明 ID 必须指向当前草稿。

`approved` 要求无阻断问题且建议修复目标为 `none`；可以保留文字或格式方面的警告。`changes_required` 必须给出具体问题和非 `none` 的建议。必需章节、计划、数据、指标、来源及版本错误不能降级为警告。

| 问题类别 | 明确含义 | `repair_target` |
| --- | --- | --- |
| `plan` | 大纲缺少需求中的必需内容 | planner |
| `data`、`source` | 数据统计、归类或证据来源错误 | data |
| `required_section` | 草稿遗漏大纲必需章节 | writer |
| `metric` | 草稿抄写指标错误 | writer |
| `version` | 草稿或审核产物版本问题 | writer |
| `content`、`format` | 叙述或格式问题 | writer |

模型的 `suggested_repair_target` 只是建议。`repair_target` 属性根据问题类别按 planner → data → writer 计算，不服从模型自行选择的路由。本批次仅计算这个值，没有运行返工流程或执行全局次数限制。

## 5 调用顺序与边界

各角色后续实现应先用 `model_validate_json()` 校验自己的结果，再依次调用：

1. `validate_plan(task, plan)`。
2. `validate_evidence(plan, evidence)`，显式处理缺项。
3. `validate_draft(draft, plan, evidence, plan_ref=..., evidence_ref=...)`。
4. `validate_review(review, draft, plan, draft_ref=..., draft_sha256=..., evidence_ref=...)`。

对象内部错误抛出 Pydantic `ValidationError`，跨对象不一致抛出 `ContractError`。这些不是业务终态；后续编排层仍须转换为设计中的错误与缺项处理。审核 `approved` 不会覆盖先前程序校验的错误，也不直接授权导出。结构对象或列表修改后，应在下一交接边界重新加载校验。

本批次只验证结构及传入对象之间的一致性。真实文件是否存在、符号链接越界、输入清单归属、SHA-256 是否对应原文件、Data 是否引用了真实工具产物、公式计算、正文语义及审核是否针对本次运行，仍由后续工具、运行服务和角色包装层核验。调用方传入的预期引用和哈希必须来自可信产物索引。
